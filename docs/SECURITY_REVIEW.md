# Production Security Review

Reviewed: 2026-09-02. Scope: application routes, server services, Prisma schema and migrations, browser shell, tests, container, CI, and operational assumptions. This is an internal code review, not an independent penetration test.

## Executive decision

The foundation is suitable for staging with synthetic data after database-backed tests pass. It is **not approved for real student data**. The release blockers are private object storage and malware scanning, working MFA for privileged users, an external security assessment, managed secrets and observability, tested restore procedures, approved retention rules, and production load evidence.

The 2026-09-02 unit coverage run passed but reported only 14.16% statement/line coverage across the unfiltered repository. Generated Prisma runtime, route files, UI, seed code, and integration-tested application services distort that aggregate, but the number still demonstrates that unit coverage is not an adequate release signal. The run also emitted missing-source-map warnings for generated Prisma runtime files. These warnings were not suppressed. Configure reviewed coverage scopes and risk-based thresholds, while retaining database integration and browser gates, before production approval.

## High-value findings fixed in this pass

- Bounded streamed request bodies replace unbounded `request.json()`, `formData()`, and CSV reads on reviewed paths.
- Tenant onboarding now uses persistent throttling; all database rate buckets serialize concurrent updates.
- Context switching and grant resolution now reject expired trust/school access and inactive roles/permissions.
- Canonical `APP_ORIGIN` defeats forwarded-host spoofing in mutation-origin checks.
- CSV exports neutralize formula-leading cells; analytics exports now append a restricted audit event.
- Readiness tests PostgreSQL without exposing connection details; liveness remains dependency-free.
- Browser responses add CSP framing/form/base restrictions, COOP/CORP, and production HSTS.
- Structured logging and error-monitor ports redact sensitive keys and omit raw exception messages.

## Explicitly reviewed attack paths

Authentication enumeration, brute force, reset replay, disabled users, stale sessions, open redirects, CSRF/Host spoofing, cross-tenant context selection, resource-ID substitution, unsafe query/body types, oversized bodies, traversal-like storage keys, private document downloads, export permission bypass, spreadsheet injection, audit mutation, database-owner RLS bypass, sensitive logging, dependency advisories, and migration destruction were inspected. No claim is made that this eliminates unknown vulnerabilities.

## Required pre-production verification

1. Run migrations, seed, integration, RLS, browser, and smoke suites on the release image and managed PostgreSQL candidate.
2. Complete external web/API penetration testing with two synthetic trusts and multiple roles.
3. Complete a backup/PITR restore drill and reconcile row counts, audit sequences, and sample hashes.
4. Exercise incident response, session revocation, key rotation, and tenant-notification decisions.
5. Approve privacy notices, data-processing terms, retention schedules, and India hosting/data-transfer posture with counsel.
